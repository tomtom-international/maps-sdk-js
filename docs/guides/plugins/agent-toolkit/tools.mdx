Tools are what the agent acts with. On each turn, the [intent classifier](./how-it-works.mdx#1-intent-classification) picks a
subset, and the [tool loop](./how-it-works.mdx#2-tool-loop) lets the model call them until it can answer. This page lists
the built-in registry and the tools with behaviour worth knowing. [Customizing tools](./customizing-tools.mdx) covers
removing, replacing and adding them.

## The `ToolEntry` shape

`DEFAULT_TOOLS` is a flat record of named tools. Each `ToolEntry` defines what a tool does and how the agent uses it:

```typescript
{
    description: string;          // Full tool description for the model
    inputSchema: ZodType;         // Validated input parameters; an object schema rejects keys it doesn't declare
    outputSchema?: ZodType;       // Structured output (improves reliability)
    execute: (input, state, options?) => Promise<any>; // never throws — returns { error } instead

    // Classifier and help metadata
    classificationPrompt?: string; // One line: when to activate this tool — what the classifier reads
    tags?: string[];               // Category labels (e.g. 'route', 'traffic')
    examples?: string[];           // Usage examples, in the metadata a custom classifier receives
    examplePrompts?: string[];     // Natural-language prompts shown by the help tool
    relatedTools?: string[];       // Tools often used together, listed by help
    dependsOn?: string[];          // Tools that must run first, shown to the classifier

    // Loop control
    alwaysActive?: boolean;        // Offered every step, whatever the classifier picked
    endsTurnOnCall?: boolean;      // Calling it ends the turn

    // Per-turn scope — see Scope-aware data tools
    scopeSchema?: ZodType;         // Shape of `toolScopes[<name>]` the classifier emits
    scopePrompt?: string;          // Explains the scope shape to the classifier
}
```

If the entry must be rebuilt per turn, a tool can also be a `ToolEntryBuilder`, a function from `ToolBuildOptions` to
`ToolEntry`. [Add a scopable custom tool](./scope-aware-data-tools.mdx#add-a-scopable-custom-tool) shows one.

### Cancellation

`execute`'s third argument carries the AI SDK's `abortSignal` for the call, which fires when the turn is cancelled:

```typescript
type ToolExecuteOptions = { signal?: AbortSignal };
```

Forward it to every service call your tool makes, so a cancelled turn also cancels the HTTP request. An aborted call
rejects with `SDKAbortError`. Because `execute` must never throw, catch it and return an error shape:

```typescript
import { SDKAbortError, discoverPlaces } from '@tomtom-org/maps-sdk/services';

execute: async ({ query }, state, options) => {
    try {
        const results = await discoverPlaces({ query, signal: options?.signal });
        return { count: results.features.length };
    } catch (error) {
        if (error instanceof SDKAbortError) return { error: 'Cancelled.' };
        return { error: `Search failed: ${error instanceof Error ? error.message : String(error)}` };
    }
},
```

Do **not** forward it into work that outlives the turn, such as a monitor's recurring tick. That work runs after the
signal has aborted. A monitor treats a rejected tick as fatal and clears its interval, so a leaked signal stops the
monitor.

## What's in the registry

| Category | Tools |
|---|---|
| **Location** | `locatePlace`, `reverseGeocode`, `getCurrentLocation`, `getViewport`, `calculateBBox` |
| **Places & search** | `discoverPlaces`, `getPOICategoryCodes`. `discoverPlaces` counts every place it finds by category, every charging station by connector type and power, and how many are open now, so "how many of each?" takes one call. Each place it lists gives its hours today, when it next closes or opens, in the place's own time, and which days it opens. Which of the unlisted places are open still takes `analyseDatasets`. Its `chargers` input finds charging stations by power and connector type, such as "at least 150 kW". `deriveDatasets` and `recallState` on a places dataset return the same counts and per-place fields. `locatePlace` of a venue returns its distance, opening hours and connectors |
| **Routing** | `setRoute`, and `editRouteWaypoints`, which replaces, removes and adds waypoints of the current route in one recalculation. Each route summary names its main roads in `via`, and says how winding it is in `timeInCurvesPercent`, the share of the drive spent in [curves](../../services/routing/curves.mdx). Each alternative also says what it adds and avoids against route 0 in `comparedToBest`, such as a toll road or a jam, so the agent compares routes without writing code. A route held up by traffic says how many jams it meets in `jams`, and where the first one is: how far in, how long, its delay and its road. These come from [`getImportantRoads`](../../core/utilities/routes.mdx#getimportantroads) and [`compareRoutes`](../../core/utilities/routes.mdx#compareroutes). A point along a calculated route, such as 1 hour into the drive or 50 km in, is `alongRoute`: `moveCamera` flies there, `discoverPlaces` and `locatePlace` search around it, and `reverseGeocode` names the place there. The agent reads it off the selected alternative of the route it already has, or the first alternative when that route is hidden, with [`getCoordinateAtRouteProgress`](../../core/utilities/routes.mdx#getcoordinateatrouteprogress), so "10 min further" never recalculates the route. A part of that route, such as the Belgian section, the last 30 km, or from 1 hour to 2 hours, is `stretch` on `discoverPlaces` (`where.route` or `maxDetour`) and `getTrafficIncidents` (`where.route`). It uses `travelTimeSeconds` and `distanceMeters`, the same fields as `alongRoute`, or `percent` of the length, and `last` for the final part. The result's `searchedStretch` names the alternative and the parts covered, and `maxDetour` searches the selected alternative with or without a stretch. Note that the agent plans routes without guidance, so a turn at a junction counts as a curve |
| **Reachable areas** | `findReachableAreas`, for isochrones and isodistances. It needs an API key with [Calculate Reachable Range](../../services/routing/reachable-ranges.mdx) access (private preview) |
| **Your own data** | `addByodSource`, `setByodLayers` — see [Bring your own data](./byod.mdx) |
| **Traffic incidents** | `getTrafficIncidents`, `clusterIncidents`, `focusIncidents`. `getTrafficIncidents` counts the incidents it fetched by category and magnitude, totals their delay and ranks the roads with the most of them, so "how many road closures?" takes one call. `recallState` on that dataset returns the same summary |
| **Live refresh** | `setDatasetMonitor`, which turns refreshing on or off for a calculated route, so its live-traffic delays stay current, or a loaded incidents dataset |
| **Traffic area analytics** | `getTrafficAreaAnalytics`. `setMapStyling` sets the look of its datasets |
| **Trackers** (geofence and proximity alerts) | `createTracker`, `clearTracker`. `recallState({ slice: 'trackers' })` lists them and what they fired |
| **Data tools** | `analyseDatasets`, `deriveDatasets`, `monitorAnalysis` — see [Scope-aware data tools](./scope-aware-data-tools.mdx) |
| **Map display** | `updateDatasetDisplay`, which shows, hides and drops the datasets of any slice, or clears the whole map. `setMapStyling` sets how they look. For places, it also sets the marker type and draws boundaries. For routes, its `focus` [rings sections](../../map/routes-sections.mdx#focusing-sections) of the selected route and zooms to them, such as its tolls, the jam with the most delay, its curviest stretch or the `A2`. Its `waypoints: false` hides a route's pins, and `planningSlots` shows the waypoints staged for the next route. For reachable areas and computed polygons, it sets the fill style, and for reachable areas the origin pins, so the agent restyles them without calculating them again |
| **Map control** | `moveCamera`, which frames a bounding box, flies to a position or a point along a route, zooms, tilts and rotates in one call. `setRoute`, `editRouteWaypoints`, `findReachableAreas`, `getTrafficAreaAnalytics` and `getTrafficIncidents` fit the camera to what they show, and their `fitBounds: false` keeps the map where it is. `setMapStandardStyle`. `setMapLocale`, which sets the language and the [view of disputed territories](../../core/geopolitical-views.mdx) that the map and later searches follow |
| **Map styling** | `setMapStyling` — what the base map shows and how it looks, every knob by its map-wide id: [Styling Foundations](../../map/styling.mdx), whole [base-map layer groups](../../map/base-map.mdx) such as 3D buildings (`groups.buildings3D.visible`), the POI icons and their categories `pois.`, the live traffic overlays and their filters `traffic.flow.` / `traffic.incidents.`, hillshade `terrain.hillshade.` and 3D terrain `terrain.elevation.`. It also applies a [map preset](../../map/styling.mdx#presets), a reset or a theme from a few colours or an image whose [accent](../../map/styling-map-colors.mdx#the-accent-what-a-theme-reaches-beyond-the-base-map) also recolours routes and place pins. It also styles every layer the agent drew, shown now or later: found places `places.`, routes `routes.` (colour, width, waypoints, [sections](../../map/routes-sections.mdx), summary bubbles), polygons and place boundaries `geometries.`, reachable areas `ranges.`, area analytics `traffic.areaAnalytics.` (display mode, metric, palette, height, filters) and fetched incidents `traffic.incidentDetails.`. Showing them, a places dataset's marker type and a polygon's fill style stay with the display tools. Each turn lists only the knob families it touches. See [Scope-aware data tools](./scope-aware-data-tools.mdx) |
| **MapLibre direct** | `getMapStyleLayers`, `setLayerProperties`, which sets the paint and layout properties of named style layers. `executeMaplibreCode` runs model-written code in your page and is off by default: [add it](./code-generation.mdx#adding-executemaplibrecode) with `createExecuteMaplibreCodeTool()` |
| **State** | `recallState`, `setDatasetMode`, `resetState` |
| **Utilities** | `clarifyIntent`, `help` |

`analyseDatasets` and `deriveDatasets` take **JavaScript** as a parameter instead of a fixed argument list, as
[Code generation](./code-generation.mdx) explains. The
[Agent Toolkit Plugin API Reference](/maps-sdk-js/api-reference/variables/plugins.createMapAgent.html) has every tool's input and output schema.

## The `help` tool

When a user asks *"what can you do?"* or *"show me routing examples"*, the model calls `help` (summary or detail, filtered
by tag or query) to surface tool descriptions, example prompts and related tools.

In your own code, `getDefaultToolPrompts()` returns every tool's `examplePrompts` as a `Record<ToolName, readonly string[]>`.
They make starter suggestions for your chat UI that stay in sync with the registry.

## Tools that read state vs. fetch data

Some tools fetch fresh data from TomTom services, and others read [state](./state.mdx). `recallState` reads and never
fetches:

- No arguments - A snapshot of the session, with the places, routes and ranges loaded, dataset modes, map style, POIs and traffic.
- `{ slice }` - The index of one slice: `places`, `routing`, `ranges`, `geometries`, `byod`, `trafficIncidents` or
  `trafficAreaAnalytics`. The `routing` index also lists the waypoints staged for the next route. `trackers` lists the
  trackers, whether each is firing, and the alerts they fired, which `sinceMs` narrows.
- `{ slice, id }` - One dataset or tracker, summarised.

When a user asks *"what were those places?"* an hour into a session, the model calls `recallState` instead of guessing.

## Asking the user with `clarifyIntent`

`clarifyIntent` asks the user to choose among a few options before the agent acts. It is `alwaysActive`, so the model can
ask mid-task. By default, the model also writes the questions as prose, for UIs without a form. If your UI renders the
tool call's questions as a form, build the tool with `rendersForm: true`:

```typescript
import { createClarifyIntentTool, createMapAgent } from '@tomtom-org/maps-sdk-plugin-agent-toolkit';

createMapAgent(map, {
    model,
    tools: { clarifyIntent: createClarifyIntentTool({ rendersForm: true }) },
});
```

- The turn then ends on the call, with no prose. Render the call's `intro` and `questions` (each with `id`, `question`,
  `options` and `multiSelect`), and send the user's choices as the next message.
- `createClarifyIntentTool` also overrides `description`, `classificationPrompt`, `examples`, `examplePrompts` and
  `alwaysActive`.

## What `getCurrentLocation` sends

`getCurrentLocation` asks for the user's position through the browser's permission prompt, and returns it to the model.
The model provider you configured receives the position with the rest of the conversation. The prompt
names only your site, not the model, so tell users in your UI that the position goes to the assistant.

By default, the tool sends only what a "near me" query needs:

| Field | Default | With `fullPrecision: true` |
|---|---|---|
| `position` | `[lng, lat]` rounded to 3 decimals (about 100 m) | the exact fix |
| `accuracy` | 111 m, or the device's accuracy when that is coarser | the device's accuracy |
| `timestamp` | not sent | the fix's timestamp |
| Fix requested | `enableHighAccuracy: false`, a fix up to 60 s old | `enableHighAccuracy: true`, a fresh fix |

To send the exact position, replace the default with `createGetCurrentLocationTool`:

```typescript
import { createGetCurrentLocationTool, createMapAgent } from '@tomtom-org/maps-sdk-plugin-agent-toolkit';

createMapAgent(map, {
    model,
    tools: { getCurrentLocation: createGetCurrentLocationTool({ fullPrecision: true }) },
});
```

To never ask for the position, remove the tool. "Near me" queries then fall back to the map view:

```typescript
createMapAgent(map, { model, tools: { getCurrentLocation: false } });
```

## `getTrafficIncidents` `where` schema

`getTrafficIncidents` takes its area as `where: { mode: 'within', … }`, with the same multi-region fields as
`discoverPlaces`: `viewport`, `boundingBox`, `queries`, `placeIds`, `geometries`, `range`, `route`. They resolve to
bounding boxes, combined into one of at most 10,000 km². Without `where`, the tool uses the viewport.

```typescript
// Current viewport
getTrafficIncidents({});

// Named area (geocoded → polygon bbox)
getTrafficIncidents({ where: { mode: 'within', queries: [{ query: 'Paris', queryAs: 'place' }] } });

// Buffered corridor around the latest route
getTrafficIncidents({ where: { mode: 'within', route: { widthMeters: 1000 } } });

// Belgian part of the selected alternative. Several parts share one bbox, so a gap between them is included.
getTrafficIncidents({ where: { mode: 'within', route: { widthMeters: 500, stretch: { includeCountries: ['BE'] } } } });

// Multi-source union
getTrafficIncidents({
    where: { mode: 'within', queries: [{ query: 'Amsterdam' }], placeIds: ['G55fc4abe-...'] },
});
```

- A named area wins over `viewport: true` when the model sends both. Strict-mode providers such as Azure and OpenAI
  fill every field.
- By default, the tool monitors (`monitor`) the incidents shown on the map every 60 s (`monitorIntervalMs`). It fetches
  only present incidents, unless `timeValidityFilter` says otherwise.
