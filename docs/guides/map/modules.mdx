A map module adds one capability to a [TomTomMap](./tomtom-map.mdx), such as showing places or routes, filtering traffic, shading terrain or restyling the whole map. Every module follows the contract this page describes:

- A module is [style-owned or data-owned](#types-of-modules), which decides its factory and how many instances a map takes.
- You configure a module at creation, then [change it](#changing-a-setting) with `applyConfig(config)`, `updateConfig(partial)` and `resetConfig()`. `getConfig()` reads it back and `events.on('config-change', …)` reports changes.
- Each module publishes its settings as a [knob catalogue](#every-setting-as-data), and `setKnob` sets any setting by its id.
- Data, configuration and layer placement are restored after every [`setStyle`](./styles.mdx#dynamic-style-switching).
- Each module has typed [user events](./user-events.mdx) that hand you your original data.
- Modules are tree-shaken, so a module you don't import isn't in your bundle.

## Types of modules

Who owns the sources and layers a module controls decides the factory you call and how many instances make sense on one map.

### Style-owned modules: `get(map, config?)`

- They control sources and layers the map style already provides under fixed, global ids, such as the base map, POIs, the traffic tiles and the terrain elevation. They display no data of their own.
- There is **one per map**. `get()` is a lookup, so a second call returns the *same* instance. Two components can each ask for the terrain without sharing a reference.
- `get(map)` without a configuration leaves its configuration as it is. With one, it applies it to the existing instance, as `applyConfig` does. `StylingFoundationsModule` merges it instead, as `updateConfig` does.
- If the style lacks their [style part](./styles.mdx#available-style-parts), the traffic and terrain modules' `get()` adds it.
- To handle events on part of what a module covers, [scope its events](./user-events.mdx#scoping-events) instead of looking for a second module.

### Data-owned modules: `create(map, config?)`

- They add the GeoJSON sources, layers and sprite images they need, and own them for their whole lifetime. Every id has a per-instance suffix.
- A map can have **many** of them. `create()` builds a new, independent module every time, for example one set of places per search or one route per plan.

## Who owns what

Everything visible on the map has exactly one owner: whoever owns its layers. Every module has knobs of its own. Each style-owned module decides **whether and how** its part of the loaded style shows. The Styling Foundations module sets the **foundations** that reach across every part: sizes, the map colours, projection and sky. Each data-owned instance decides everything about the layers it adds itself. The dashed line is the only place a knob reaches past its module, where the data-owned modules read the accent as their default colour.

In detail:

| You want to change… | Owner | How |
| --- | --- | --- |
| **Whether** something the loaded style draws is shown — a base-map layer group or road part, the traffic tiles, a POI category, the hillshade, the 3D surface | The style-owned module for that part | `setVisible`, `updateConfig({ filters })`, `setHillshadeVisible`, `setElevationVisible`, `setKnob` |
| **How one part** looks — POI size and label colours, traffic colours and widths, hillshade lighting | The style-owned module for that part: [POIs](./pois.mdx#appearance), [traffic flow](./traffic-flow.mdx#appearance), [traffic incidents](./traffic-incidents.mdx#appearance), [terrain](./terrain.mdx#appearance) | `setKnob`, `updateConfig` |
| **The foundations** across every part — label, icon and road sizes, the ten map colours, projection and sky | The [Styling Foundations module](./styling.mdx) | `setKnob`, `setMapColors` |
| A named bundle of looks across those modules | [`applyMapPreset`](./styling.mdx#presets) | `applyMapPreset(map, id)` |
| Anything a data-owned module draws itself — routes, places, geometries, your GeoJSON, fetched traffic incidents, area analytics | That module, through its own configuration | `create(map, config)`, `applyConfig` / `updateConfig`, `setKnob` and `setVisible` |
| The map's colour identity — the [accent](./styling-map-colors.mdx#the-accent-what-a-theme-reaches-beyond-the-base-map) routes, places and geometries default to | The Styling Foundations module publishes it; each data-owned module reads it | `setMapColors`, the `colors.accent` knob; a colour set on the module always wins |
| A look a data-owned module [borrows from the style](./styling-borrowed-looks.mdx), such as POI-looking places or the colours of fetched traffic incidents | The module whose knob restyles it sets it on the style; the data-owned module reads it and redraws its own layers | The knobs that restyle what it borrows; a setting given to the module always wins |

Two consequences:

- The rows don't cross. Knobs on the loaded style never write a data-owned module's layers, and a data-owned module never restyles the base map under it. You recolour a route in the `RoutingModule` configuration, and the roads it runs on with `colors.roadMajor`. The accent and the borrowed looks are read, not written.
- The foundations and a part's own look meet on the same layers, and **compose**. One engine per map applies every style knob, whichever module holds it. So `labels.sizeFactor` and the POIs' `sizeFactor` multiply on the POI labels, and all of them land on top after a style switch.

Within a style-owned module, the finer settings only narrow what its coarser ones show. A road part or the POI micro markers never show while their layer group or the POIs are hidden. Showing those again keeps a part's `false`. The POIs' `zoomShift` rewrites the same layer filters that `filters.categories` narrows, in either order.

Each module guide opens with a *What this module owns* line that applies this rule.

## Changing a setting

Each module has three calls that change settings. `applyConfig(config)` replaces the whole configuration, `updateConfig(partial)` changes the top-level properties you give it, and `setKnob` sets one setting by its [catalogue id](#setting-a-knob-by-its-id).

- `updateConfig` **merges one level deep**. A nested object you give it replaces the current one. To change one nested field, spread the current part or set its knob:

  ```javascript
  import { placesKnobCatalogue, setKnob } from '@tomtom-org/maps-sdk/map';

  placesModule.updateConfig({ label: { ...placesModule.getConfig()?.label, color: '#c2185b' } });
  setKnob(placesModule, placesKnobCatalogue, 'label.color', '#c2185b');
  ```

- Named setters are for visibility, such as `setVisible` / `isVisible` and those of the parts that hide on their own (see *Visibility* under [Appearance vocabulary](#appearance-vocabulary)). The only others are `TrafficAreaAnalyticsModule`'s per-metric `setPalette`, `setColorStops`, `setHeight` and `setFilters`. A named setter is always `set<Setting>`.

## Saving and replaying a configuration

`getConfig()` exports a configuration and `applyConfig()` imports it. A configuration that went through JSON and back into `applyConfig` holds the same settings and draws the same layers. Keep one to restore a user's map, attach it to a support report, or replay it in a test.

```javascript
localStorage.setItem('places', JSON.stringify(placesModule.getConfig()));

// Later, on the same module or a new one
placesModule.applyConfig(JSON.parse(localStorage.getItem('places')));
```

Most module configurations, styling knobs included, are fully JSON. Five modules also take functions or image elements, which JSON can't carry. Each has a type for the part that survives, detailed on its reference page. When you replay, add the rest back in code:

| Module | Serializable part | Left out |
| --- | --- | --- |
| `PlacesModule` | `PlacesModuleSerializableConfig` | `label.title` as a function, `connections.label.title`, `icon.mapping`, `extraFeatureProps` functions, image elements in `icon` |
| `RoutingModule` | `RoutingModuleSerializableConfig` | `waypoints.icon.mapping`, `waypoints.label.title` as a function, image elements in `waypoints.icon` |
| `GeometriesModule` | `GeometriesModuleSerializableConfig` | `transformFeaturesForDisplay` |
| `ReachableRangesModule` | `ReachableRangesModuleSerializableConfig` | `lineLabel.title` |
| `CustomGeoJSONModule` | `CustomGeoJSONModuleSerializableConfig` | `images` |

`JSON.stringify` silently drops a function, but turns an image element into `{}`, which doesn't replay. To keep the whole configuration serializable, give icon images as URLs, data URIs or SVG text, and a place or waypoint title as a MapLibre expression. `POIsModule`'s `icon.categoryIcons` also takes image elements, with no type that leaves them out.

```javascript
const state = JSON.parse(saved); // PlacesModuleSerializableConfig
placesModule.applyConfig({
    ...state,
    connections: { ...state.connections, label: { ...state.connections?.label, title: (connection) => connection.name } },
});
```

The configuration is what a module draws with, not the data it shows, so replay `show()` with the data too.

## Every setting as data

Each module publishes its display settings as a knob catalogue, static data you can read with no map loaded. A control panel builds its controls from it, and an agent checks values against it. An entry's `id` is the setting's path in the module's configuration, and never points into a list. A list is one knob of kind `colors`, `enums` or `offset`, or no knob. The `kind` says which value the entry takes and which fields come with it. The entry type is `KnobEntry`, and the kinds are `KnobKind`:

| Kind | Value | Fields |
| --- | --- | --- |
| `toggle` | `true` or `false` | |
| `factor` | a multiplier, `1` keeping what the style does | `range` |
| `number` | a number | `range` |
| `offset` | an `[x, y]` displacement, x to the right and y down, in the unit the description names | `range`, for x and y each |
| `color` | a CSS colour | |
| `enum` | one of the options | `options` |
| `enums` | a list of the options; the description says when their order matters | `options` |
| `colors` | a list of CSS colours or of the names in `options` | `options`, where there are names |
| `image` | the id of an image in the style's sprite | |
| `text` | any string | |

- `range` is the span a control offers, with the `step` a slider uses. Its `bounds` say which ends a value must keep to:

  | `bounds` | A value must be | For example |
  | --- | --- | --- |
  | `hard` | between `min` and `max` | an opacity, a `*Factor` |
  | `hard-min` | at least `min`; above `max` it still applies | a height in metres |
  | `soft` | any number | an offset |

- `default` is present where one value holds everywhere. Otherwise, the description says what decides, such as the style, the accent or the global configuration.
- A setting that takes a MapLibre expression, a callback or a structured object stays in the configuration. If a setting also takes an expression, its entry holds the plain-value alternatives, which the module's `…KnobValueOf<ID>` type names.
- The [styling catalogue](./styling.mdx#the-knob-catalogue) and the [map effects plugin](../plugins/map-effects.mdx) catalogue use the same kinds.

### Setting a knob by its id

Three functions work with a knob by its catalogue id on every module, including the [Styling Foundations module](./styling.mdx) and the [map effects plugin](../plugins/map-effects.mdx)'s `MapEffects`:

- `setKnob(module, catalogue, id, value)` - Sets one setting and keeps every other one. A value its entry refuses changes nothing.
- `getKnob(module, catalogue, id)` - Reads the value in force: the value you set, otherwise what the module knows it to be (a look knob of a style-owned module reads the loaded style), otherwise the entry's `default`.
- `resetKnob(module, catalogue, id)` - Unsets one setting and drops the objects it leaves empty, so a knob you set and then reset leaves the configuration as it was. `resetConfig()` unsets them all.

- `knobEntryOf(catalogue, id)` - Reads one entry: kind, range or options, default and description.
- `validateKnobValue(entry, value)` - Runs the check alone, for a value from a form or a language model.
- `validateKnobValue` and `setKnob` throw a `RangeError` naming the knob and what it expects. The four that take an id throw an `Error` for an id the catalogue lacks.
- A literal id types the value it takes. An id held as any `string`, as in a panel looping over a catalogue, takes any value and is checked when set.

The path is the same for every module, and a knob only ever redraws what its own module draws:

```d2
direction: right

Catalogues: "One catalogue per module\nstatic data, no map needed" {
  style: {
    fill: "#e8f5e9"
    stroke: "#1b5e20"
```
