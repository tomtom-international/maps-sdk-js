The Styling Foundations Module holds what every part of the map shares, as **semantic knobs**: label, icon and road sizes, the ten map colours and the accent, a globe with a sky.

- Each knob reaches across the whole style. `labels.sizeFactor` resizes every label, POIs and road shields included, and `colors.roadMajor` recolours every shade of the major roads. The other style-owned modules each hold the look of [one part](#every-knob).
- The knobs are semantic, not layer ids. Like every module's settings, they are validated and listed as data in a [knob catalogue](#the-knob-catalogue). MapLibre layers you edit by hand, through [`styling.layers`](./styling-layers.mdx) or `map.mapLibreMap`, have no catalogue and depend on the layer ids of one style version.

## Initialization

```javascript
import { TomTomMap, StylingFoundationsModule } from '@tomtom-org/maps-sdk/map';

const map = new TomTomMap({ mapLibre: { container: 'map' } });
const styling = await StylingFoundationsModule.get(map);
```

Pass settings to apply them right away, for instance restored from storage:

```javascript
const styling = await StylingFoundationsModule.get(map, { 'labels.sizeFactor': 1.2, 'colors.water': '#0fa8c8' });
```

- A map has one module. A second `get()` returns the same instance and merges the settings passed to it over what it holds.
- The map is themed from the first frame. `get` resolves once the style has loaded, before the map draws it. Knobs you pass to `get` or set right after it land on that frame instead of fading in from the style's own look ([Themed map](../../examples/themed-map)).

## Knobs

Every adjustable thing is a knob with a stable id. Set one with `setKnob`, read it with `getKnob`, and restore the style's own value with `resetKnob`, [as on every module](./modules.mdx#setting-a-knob-by-its-id):

```javascript
import { getKnob, resetKnob, setKnob, stylingFoundationsKnobCatalogue } from '@tomtom-org/maps-sdk/map';

const knobs = stylingFoundationsKnobCatalogue;
setKnob(styling, knobs, 'labels.sizeFactor', 1.3);    // every base-map label 30% bigger
setKnob(styling, knobs, 'roads.widthFactor', 0.8);    // thinner roads, hierarchy kept
setKnob(styling, knobs, 'colors.roadMajor', '#f59e0b');
setKnob(styling, knobs, 'view.projection', 'globe');

getKnob(styling, knobs, 'roads.widthFactor');   // 0.8
resetKnob(styling, knobs, 'roads.widthFactor'); // back to the style's width
styling.resetConfig();                          // everything back to the style as shipped
```

### How knobs work

- Most knobs write the loaded style's layers. The `view` knobs write the map itself. `colors.accent` writes nothing, and the modules that draw their own layers read it.
- One engine per map applies the knobs, and the look knobs of the POIs, traffic and terrain modules restyle the same loaded style through it. Knobs on one layer property compose, whichever module set them. For example, `labels.sizeFactor` here and `sizeFactor` on `POIsModule` multiply on the POI labels. All of them land again after a style switch.
- **No knob shows or hides a layer group** (water, 3D buildings, road shields). The [Base Map Module](./base-map.mdx) does that.

| Kind | Takes | What it does |
| --- | --- | --- |
| factor | a multiplier, `1` = as the style ships | multiplies the style's own value, so zoom ramps and the road hierarchy are kept. A zoom ramp has each stop's output scaled, and any other expression `E` becomes `["*", 1.3, E]` |
| colour | any CSS colour | replaces the colour and re-derives the shades the style built from it. Recolouring the major roads recolours their darker outline by the same offset. `colors.accent` paints no layer, and the modules read it |
| toggle | `true` / `false` | `view.sky.visible` turns the sky on or off |
| enum | one of the knob's options | picks a mode, here the projection |

Every knob also follows the same rules:

- A value outside its range or of the wrong kind throws a `RangeError` naming the knob and what it takes. An unknown id throws an `Error`. A failed call changes nothing.
- `getKnob` reads the value in force: the one you set, or the loaded style's own. It returns `undefined` where the style computes the value from the data, and `resetKnob` still restores it.
- Knobs are re-applied after every `setStyle`, and a clean switch drops them ([Style changes](#style-changes)).
- `getConfig()` returns the knobs you set as plain data, ready to store and re-apply ([Settings](#settings-persist-share-re-apply)).
- The ten map colours follow the TomTom styles' taxonomy, re-verified on every style release. Every other knob needs no knowledge of the style ([How durable is this?](#how-durable-is-this)).
- Knobs reach only the style's layers and the map's view. What the SDK draws itself (routes, places, geometries) is configured on its own module. It defaults to [the accent](./styling-map-colors.mdx#the-accent-what-a-theme-reaches-beyond-the-base-map), and a few of its parts [borrow a look](./styling-borrowed-looks.mdx) from the style.

### The knob catalogue

[`stylingFoundationsKnobCatalogue`](/maps-sdk-js/api-reference/variables/map.stylingFoundationsKnobCatalogue.html) lists every knob as static data, readable with no map loaded. Its entries share the shape of every module's catalogue ([Every setting as data](./modules.mdx#every-setting-as-data)):

```javascript
import { getKnob, stylingFoundationsKnobCatalogue } from '@tomtom-org/maps-sdk/map';

for (const knob of stylingFoundationsKnobCatalogue) {
    // knob.id, knob.kind ('factor' | 'toggle' | 'color' | 'enum'), knob.description,
    // knob.range (factor), knob.options (enum), knob.appliesTo
    const current = getKnob(styling, stylingFoundationsKnobCatalogue, knob.id);
}
```

- Entries have no `default`, because the loaded style decides. On a live map, `getKnob` reads the value in force.
- `stylingFoundationsKnobIds` lists the ids on their own, typed `StylingFoundationsKnobId`. `StylingFoundationsKnobValueOf<ID>` is the value one takes, and `stylingFoundationsKnobKinds` lists the kinds.
- Each control of the playground at the top of this guide shows the value `getKnob` reads.

Every colour a knob sets on the loaded style, whichever module holds it, also has a **map-wide id**: the module's prefix, then its id in that module's catalogue. The Styling knobs keep their own ids (`colors.water`). The others take `pois.`, `traffic.flow.`, `traffic.incidents.` or `terrain.` (`pois.label.color`, `traffic.flow.colors.slow`, `terrain.hillshade.colors.shaded`). `styleColorKnobIds` lists them, typed `StyleColorKnobId`. [`getStyleColor`](/maps-sdk-js/api-reference/functions/map.getStyleColor.html) reads the colour one is at (the one set, one the style derives from the map colours, or the style's own), whether or not its module exists:

```javascript
import { getStyleColor } from '@tomtom-org/maps-sdk/map';

getStyleColor(map, 'colors.water');
getStyleColor(map, 'traffic.incidents.colors.major'); // undefined where the style colours it by an expression
```

Name a map colour through them rather than hard-coding it, as the [map effects plugin](../plugins/map-effects-bloom.mdx#scoping-bloom-by-colour) does to scope its bloom. `StyleKnobId` and `StyleKnobValueOf<ID>` type every style knob by its map-wide id.

When you wire controls to the catalogue, copy two things from the playground:

- Call `setKnob` once per animation frame at most. A slider or a colour picker fires `input` far faster than a restyle runs, so coalesce the calls (last value wins) and apply the final value on `change`.
- Rebuild the panel on external changes only. `setKnob` emits `config-change`, so rebuilding from it mid-drag replaces the input under the pointer. Skip the changes your own controls made, and rebuild on a reset, a `setStyle` or an agent.

## Presets

A map preset is a named bundle of knob settings for a common intent. It sets knobs across the modules that hold the look of the map: this one, `BaseMapModule`'s road parts and `POIsModule`'s look. [`mapPresetCatalogue`](/maps-sdk-js/api-reference/variables/map.mapPresetCatalogue.html) lists them with the settings each one applies, per module, by that module's catalogue ids (`MapPresetSettings`):

| Preset | Intent |
| --- | --- |
| `data-viz` | A quiet base for your own data on top: smaller labels and icons, thinner roads, no exit badges or road arrows, no POI dots, POIs from zoom 14 |
| `night-driving` | Bigger labels and icons, wider roads, exit badges and road arrows shown, no POI dots, POIs from zoom 13 |
| `minimal` | The bare map: smaller labels, no road markings or exit badges, no POI dots, POIs from zoom 16 |
| `globe` | Globe projection with a sky |

```javascript
import { applyMapPreset, setKnob, stylingFoundationsKnobCatalogue } from '@tomtom-org/maps-sdk/map';

await applyMapPreset(map, 'data-viz');                            // replaces what the other presets set
setKnob(styling, stylingFoundationsKnobCatalogue, 'labels.sizeFactor', 1.1); // then adjust
await applyMapPreset(map, 'globe', { merge: true });              // lay a preset over what is there
```

- [`applyMapPreset`](/maps-sdk-js/api-reference/functions/map.applyMapPreset.html) is async, and creates the Styling, Base Map and POIs modules if the map has none yet. Their `get()` returns those same instances.
- By default, the knobs any preset sets are reset before this one applies, so nothing of the last preset stays. Every other knob keeps its value. `{ merge: true }` skips the reset.
- Whole layer groups stay as the style ships them. To hide buildings or shields, use [`BaseMapModule`](./base-map.mdx).
- An unknown id throws an `Error` listing the known ones, `mapPresetIds`. `MapPresetId` is their union, and `MapPreset` an entry of the catalogue.

A preset is exactly as durable as the knobs it sets. For the visual half of the `data-viz` intent, dimming and desaturating what remains, pair it with the map effects plugin's [grade and tint](../plugins/map-effects-overlays.mdx).

## Exporting the style

`exportStyle()` returns the map's style as currently rendered, as a MapLibre style specification. This is the loaded style with every knob applied, plus whatever the SDK's data modules (places, routes) have added to it. Save it, diff it, or serve it yourself.

- **Tile URLs carry the API key** the map was created with, so strip or rotate it before publishing the file.
- `map.getStyleInput()` returns the style input instead: the id or object the map was given ([Map styles](./styles.mdx)).

## Settings: persist, share, re-apply

`getConfig()` returns the overridden knobs as a plain object (`StylingFoundationsModuleConfig`). `applyConfig()` replaces every knob with one, and `updateConfig()` sets the ones given and keeps the rest. It serializes cleanly, so styling can live in local storage, a URL or a pull request. It keeps working on a later SDK version for as long as the knob ids do:

```javascript
localStorage.setItem('map-styling', JSON.stringify(styling.getConfig()));
// …later
styling.applyConfig(JSON.parse(localStorage.getItem('map-styling')));

styling.events.on('config-change', (settings) => save(settings));
```

## Style changes

The style (`style` on the map, or `setStyle`) decides which map document loads. Knobs adjust whichever one is loaded.

- `map.setStyle(...)` re-applies the knobs once the new style has loaded, after the other modules have restored themselves, so they land on top, on the new style's first frame.
- A clean switch (`resetState: true`) drops them, with the rest of the SDK state ([Keeping or dropping state](./styles.mdx#keeping-or-dropping-state)).

## How durable is this?

There are two kinds of knobs, told apart by `appliesTo` in the catalogue:

- `any-style` knobs need no knowledge of the style, so they hold whatever the style version:
  - the factors, which wrap whatever the style already does;
  - the `view` knobs, which set the map's projection, sky and background rather than a layer;
  - `colors.accent`, which paints no layer at all.
- `tomtom-styles` knobs, the ten map colours, reach their layers through a taxonomy the TomTom styles declare. The SDK re-verifies them against the styles it ships with. On a style that doesn't declare the taxonomy, setting the knob warns once in the console and does nothing.

Nobody re-tests a `setPaintProperty` against a layer id when the style changes version. A knob is re-verified on every style release the SDK ships.

## Interplay with other modules

[Who owns what](./modules.mdx#who-owns-what) states which module owns which layers. In short:

- This module holds the foundations that reach across every part: sizes, map colours, the accent, projection and sky.
- The other style-owned modules each hold one part: whether it is shown, which of its features show, and how it looks ([Every knob](#every-knob)). Where a foundation and a part's own knob reach the same layer, they compose, and a [map preset](#presets) sets both at once.
- Data-owned modules (routes, places, geometries, [your own GeoJSON](./custom.mdx)) draw their own layers, styled through their own configuration. No knob writes them.
